# 受注システム MVP 基本設計書

Sep 18, 2026 · @よしみ

## システム概要

### 目的

鋼材の切断・加工を行う事業所を想定し、20 年近く稼働している基幹システムのうち、鋼板切断部門が担う業務を対象に、紙伝票と Excel に分散した情報を一元化する受注管理システムを構築する。

現状の業務では、同一の受注情報が形を変えて何度も転記されている。加工指示書、製品ラベル、配送日報、ショット加工量明細は、いずれも元をたどれば受注情報であり、それぞれ別の Excel や紙に手作業で書き写されている。受注をデータとして一度登録すれば、あとは用途に応じて表示や出力の形を変えるだけで足りる。この転記の解消が本システムの中心的な狙いである。

### 対象範囲

本システムが担うのは、既存の基幹システムにおける鋼板切断部門の日次業務である。将来的には材料調達・加工・配送など他部門との連携も視野に入れるが、本設計書では扱わない。

### MVP の位置づけ

MVP では、鋼板切断部門の業務のうち **受注登録・受注管理** に焦点を当てる。受注登録は現場へ加工を回す行為そのものであるため、加工指示書の印刷は受注登録機能と一体として扱う。送り状発行についても、受注から出荷までの一連の流れが通ることを重視し、MVP に含める。

受注登録は現場へ加工を回す行為そのものであるため、現場に渡る一式（加工指示書・加工図面・製品ラベル）は受注登録と同じタイミングで出力する。ミルシート作成は Phase2 以降に実装する。

### 判断の根拠

帳票出力は PDF ファイル生成ではなくブラウザ印刷（CSS の `@media print`）で実装する。現行の 3 枚複写（控え・現場用・単価記入用）は物理的な複写の都合によるものであり、デジタル化後は単価の表示・非表示を切り替えるだけで代替できる。

加工賃の自動計算は、加工種別が多く条件も複雑（穴は板厚と穴径、開先は板厚・長さ・角度で単価が決まるなど）であるため、MVP では手入力とする。母材費については判定軸が明確なため自動計算の対象とする。ただし将来の自動計算に備え、加工の内容は自由な文章ではなく、単価の決定要素となる項目（穴径・孔数・曲げのヶ所数など）で入力する（「加工の入力項目」を参照）。

## 画面構成

ホームから部署を選び、部署のサイドメニューに業務メニューが並ぶ階層構造とする。鋼板切断部門は「シャーリング部」として表示する。画面の枠（ヘッダー・サイドメニュー）は screen-design.md「共通レイアウト」を参照。

```
ホーム（社内連絡・目安納期）
  ├ 部署：営業部 / 加工部 / シャーリング部 / 配送部 / 経理・総務   ← シャーリング部以外はメニューのみ
  ├ 営業所：A営業所 / B営業所                                    ← メニューのみ
  └ 共通：受注管理 / 在庫管理〔提案〕 / 社内連絡 / マスタ管理

シャーリング部
  ├ 部署ホーム
  ├ 受付登録（受付待ち・振り分け）    ← MVP（docs/intake/）
  ├ CAD                              ← MVP（docs/intake/）
  ├ 受注登録（受注登録待ち → 受注情報 → 注文内容）← MVP
  │   └ 現場用伝票の印刷
  ├ 加工図面発行（加工図面・製品ラベルの印刷）   ← MVP
  ├ 送り状発行                       ← MVP
  ├ ミルシート作成                   ← Phase2
  ├ 受注管理                         ← MVP
  ├ 納期連絡                         ← MVP（docs/intake/）
  ├ 在庫・材料〔提案〕
  └ マスタ管理                       ← MVP
```

「メニューのみ」の項目は、サイドメニューに表示するが押せない（準備中）とする。

### 各画面の役割

**受注登録・受注管理**

受注の新規登録、編集、一覧表示を担う。新規登録は受注登録待ち（振り分けや CAD が終わった加工区分の一覧）から始め、① 受注情報 → ② 注文内容（明細と、その下のスタンプ・フリーコメント）の 2 つの画面で入力する（screen-design.md「受注登録画面」）。受注登録は現場へ加工を回す行為そのものであるため、加工指示書の印刷はこの画面の流れの中に置く。一覧では、ステータス・納期種別・得意先などで絞り込み、過去の受注を参照できる。リピート注文が多いため、過去受注の検索性を重視する。

受注登録の画面には仕入単価を出さない。単価の確認・入力は、送り状の発行後に「仕入入力」の画面で行う（後述「仕入入力」）。

**送り状発行**

納期が確定し、加工が完了した受注に対して出荷を記録する。受注時点では納期が未確定の注文が多いため、受注登録とは別のタイミングで実行される独立した画面とする。分割出荷に対応し、出荷のたびに実績を積み上げる。

**マスタ管理**

得意先・納入先・商品・価格・加工種別・メーカー・営業所・納期連絡の工程などの各マスタを登録・編集する。価格マスタは仕入単価を含むため、管理者のみアクセス可能とする。

**現場加工指示**

現場用伝票のチェックを終えた受注に対して、加工図面と製品ラベルを印刷する。過去の受注を開いて再発行することもできる。

### 画面遷移の方針

現場用伝票は受注登録と同時に印刷する。スタンプ文言やフリーコメントを含め、伝票に載る内容はすべて受注入力時に入力するため、登録した時点で伝票の内容が確定するからである。印刷を別の画面に分けると、受注データと伝票の内容に差異が生じる余地を残すことになる。

加工図面と製品ラベルを別メニューとするのは、印刷した現場用伝票と注文書を照合するチェック作業を挟むためである。誤った内容のまま現場に一式が流れることを防ぐ。

## 業務フロー

### 全体の流れ

```
受付（メール・FAX・口頭）→ 受付登録 → 振り分け（先寸／アイトレ）→（アイトレは CAD）
  ↓  ［受注登録待ち］           ← docs/intake/basic-design.md「業務フロー」
受注登録（受注情報 → 注文内容。母材費の自動計算・注意事項の表示・スタンプ文言・フリーコメント）
  ↓
現場用伝票を印刷
  ↓
印刷した伝票と注文書（受付で保存済みの PDF）を照合してチェック
  ↓
現場加工指示メニューから加工図面・製品ラベルを印刷し、現場へ回す
  ↓  ［加工待ち］
加工完了・現場用伝票が事務所に戻る
  ↓  ［出荷待ち］
送り状発行（出荷数量を入力）
  ↓  ［配送依頼済み］
全数出荷完了
     ［完了］
  ↓
仕入入力（単価の確認・別途見積もりの単価の入力・仕入の計上）← 予定（後述「仕入入力」）
```

業務の流れは「受注 → 送り状 → 仕入」の順に進む。修正はこの逆順でしか行えない（仕入を削除 → 送り状を削除 → 受注を修正）。

### ステータス

ステータスは受注ヘッダーに 1 つ持つ。実務では同一受注内の明細がまとめて加工・出荷されるため、明細単位のステータス管理は行わない。

| ステータス | 意味 | 遷移のきっかけ |
| --- | --- | --- |
| 加工待ち | 受注登録済み、加工中 | 受注登録時に自動設定 |
| 出荷待ち | 加工完了、出荷可能 | 現場用伝票が戻った時点で事務が更新 |
| 配送依頼済み | 送り状発行済み、出荷進行中 | 送り状発行ボタン |
| 完了 | 全数出荷済み | 残数量がゼロになった時点 |

### 納期の扱い

納期は「種別」と「日付」の 2 つで保持する。日付の有無だけでは実務上の区別がつかないためである。

| 種別 | 日付 | 意味 |
| --- | --- | --- |
| 確定 | あり | 客先と合意済み |
| 仮納期 | あり | 自社で見込みを立て客先に回答した段階。未確定 |
| 後報 | なし | 全く未定。客先からの連絡待ち |
| 最短出荷 | なし | 日付未定だが加工完了次第すぐ出荷 |

仮納期は現行システムでは入力できず、現場用伝票に手書きで記入して運用している。システムに存在しない情報が現場に流れている状態であり、これを画面上で追えるようにする。

後報と最短出荷はいずれも日付が未定だが、前者は「待ち」、後者は「急ぎ」であり現場での意味が異なる。一覧で最短出荷の案件を識別できることに実務上の価値がある。

受付にも同じ種別と日付で納期を持つ（初期状態は 3 後報）。1 つの受付の中で納期が分かれることがあるため、本当の納期は受注（枝番）ごとに持ち、受付の納期は受注の初期値と受注登録待ちの並び順に使う代表の納期とする。受注の納期の初期値は、受付に日付があれば「1 確定」＋その日付、日付がなければ「3 後報」とする（受付で仮納期・最短出荷を選んでいればその種別）。受注で納期を変えても、受付の納期は書き換えない（docs/intake/basic-design.md「納期の決まり」）。

受付の「至急」は、受注登録待ち・CAD で先頭に並べるための事務所内の印であり、納期種別の「最短出荷」（客先への出荷の約束）とは別のものである。

納期変更は頻繁に発生するが、MVP では現在の納期のみを保持し、変更履歴は持たない。将来的に物件単位の工程一覧を実装する際、納期変更や注文変更のやり取りを備考・チャット形式で記録する構想があり、履歴管理はそちらと一体で設計する。

### 分割出荷

分割出荷はステータスではなく出荷実績の積み上げで表現する。残数量は「受注数量 − 出荷実績の合計」として動的に算出し、カラムとしては保持しない。出荷の取り消しや修正が発生した際に整合性が崩れることを避けるためである。

## 主要機能の仕様

### 受注登録

受注はすべて受付を通し、受注登録待ちの加工区分から登録する。口頭・電話の注文も、受付の「手動で受付を追加」から受付を作る。

受注番号は「受付No.＋枝番」（例: `26-1003-1`）とし、登録時にシステムで自動採番する。1 つの受付から複数の受注を登録でき、枝番は受付ごとの連番になる（docs/intake/basic-design.md「用語」）。以前の「年 2 桁＋連番 5 桁」（`2600001`）の採番は使わない。

受注情報（売り先・納入先・工事名・納期・配達など）は、受付登録と同じ入力欄を使い回し、受付で入れた値を初期値にする（docs/intake/basic-design.md「受注情報」）。必須は売り先だけとする。受注日と担当者（自社の担当者）は、今日とログイン中のユーザーを自動で入れ、変更もできる。担当者は加工指示書にも印字する。登録の操作をした人は、担当者とは別に記録する（`orders.created_by`）。

**保存の方法**

ヘッダーと明細は 1 回の操作でまとめて保存し、途中で失敗した場合は全体を取り消す（ヘッダーだけが登録された中途半端な受注を残さない）。そのため、登録は DB の関数 `create_order` で 1 つの transaction として行う（table-design.md「受注の登録（create_order）」を参照）。

入力内容の確認は画面とサーバーの両方で同じ関数を使って行う。重量・仕入単価はサーバー側でも計算し直し、画面から送られた単価は使わない。何も入力していない明細の行は保存しない。明細が 1 行もない受注は登録できない。

仕入単価は受注登録の時点で自動計算して保存するが、受注登録の画面には表示しない。現行システムと同じく、単価の確認・入力は別の画面「仕入入力」で行う（後述「仕入入力」）。受注入力では明細の内容（切断・材質・寸法・数量）に集中し、単価のイレギュラーは送り状を発行した後にまとめて扱う。

**用語：仕入単価**

本書で自動計算する単価（切断単価・特殊製品単価・定尺単価に各エキストラを加算した kg 単価、およびそこから求める枚単価）と金額は、すべて **仕入単価・仕入金額** である。受注明細では `order_items.cutting_unit_price` に保存する（列名は切断単価に由来するが、定尺売り・特殊製品を含めて仕入単価を保持する）。

売上単価は営業が決めるものであり、MVP の対象外とする。将来の営業システム連携（Phase2）で扱うため `order_items.sales_unit_price` は残すが、MVP では使用しない。

**受注入力で扱わないもの**

受注入力の手間を増やさないため、受注時点で決まらないもの・別の業務で扱うものは受注登録画面で入力しない。

| 項目 | 扱い |
| --- | --- |
| 梱包数 | 受注後のラベル発行メニューで入力する |
| 実重量（手入力が必要なもの） | 送り状発行の画面で、必要な行だけ入力する |
| 仕入単価・仕入金額 | 自動計算して保存するが、画面には出さない。別途見積もりの単価は空欄のまま登録し、仕入入力の画面で入力する |
| 加工の単位・加工の仕入単価 | 仕入入力の画面で扱う（受注登録では単位を「個」、単価を空欄で保存する） |
| 売上単価 | MVP の対象外（上記） |
| フリー区分（重量の手入力） | MVP では作らない。必要になれば追加する |

**入力方式**

1 件の受注で明細が 100 行を超えることもあるため、テンキーだけで入力を完結できるコード入力とする。選択する項目はすべて番号で入力し、番号を打つと名称が表示される。初期値がある項目は Enter だけで次へ進める。最も多く使う値に番号 0 を割り当てて初期値にする（「0 はいつもの値」。例: 入れ先 0 売り先と同じ、種類 0 普通板、材質 0 SS400、メーカー 0 指定なし）。欄の移動は Enter・Shift+Enter のほか、↑↓ でも行える。キー割り当ては現行システムに合わせず、ブラウザの標準操作と衝突しないよう独自に設計する。

明細は 1 件 1 行の表とし、切断方法と区分は 1 つの 2 桁の番号（例: 41 レーザー寸法切、42 レーザーアイトレ、71 定尺）で入力する。種類・材質・製鋼法・メーカーは常に列として表示し、初期値と違う値（高炉の指定・メーカー指定・縞板など）は強調して見落としを防ぐ。注文書は画面の左のパネルに表示し、見ながら入力する（screen-design.md「受注登録画面」）。

**スプライス専用の受注**

スプライスは通常の明細と混ざることがないため、明細の区分ではなく受注単位で切り替える。受注情報の部材区分（DF / GPL / BH / SPL / 無分類）で **SPL を選んだ受注がスプライス専用の受注** になる。部材区分とは別にスプライスの印を持つと、両者が食い違うおそれがあるため、1 つにまとめる。スプライス専用の受注では、継手番号とショットの有無を受注に持ち、明細はすべてスプライスとなる（詳細は「特殊製品の単価」を参照）。

部材区分は、部品ごとに受注を分けるときに使い、後の工程管理で利用する。

画面の入力項目・入力順・キー操作・番号は screen-design.md「受注登録画面」を参照。

**明細の構造**

明細は「受注明細（材料）」と「加工明細」の親子構造とする。

```
受注明細（材料 1 品目）
  ├ 商品（材質 × 板厚 × 形状）、切断方法、寸法、数量、重量
  └ 加工明細（0〜複数行）
      └ 加工種別、加工の項目（穴径・1 枚あたりの孔数など）、数量、加工賃
```

価格は「母材費 + 切断賃 + 加工賃」で構成される。切断方法はシャーリング・ガス・レーザー・プラズマの 4 種類で、母材に切断賃を加えた価格が基本となる。これとは別に、母材の価格のみの定尺売りがある。加工には穴あけ（レーザー・プラズマ孔・ガス孔）、キリ孔、曲げ、開先、ショット、タップ孔、マーキング、ピアス孔、切り込みなどがあり、加工種別マスタで管理する。レーザー孔とプラズマ孔は単価が同じため、1 つの加工種別（レーザー・プラズマ孔）にまとめている。

加工指示書では穴あけなどの加工行が重量ゼロの別行として印字されるが、これは表示上の処理であり、データ構造としては材料に紐づく加工明細として保持する。

### 加工の入力項目

加工の内容（伝票の「1S/ 12孔 38φ」のような文）は、自由な文章ではなく項目で入力する。加工賃は加工種別ごとに決定要素（穴径・孔数・ヶ所数など）が異なり、将来の自動計算にはそれらが項目として取り出せる必要があるためである。

**入力の形**

加工種別マスタに「入力の形」を持たせ、形ごとに入力欄を切り替える。加工種別の名前で分岐せず、データとして持つ（特殊製品種別の「寸法の形」と同じ考え方）。同じ項目で入力する加工種別（レーザー・プラズマ孔・ガス孔・キリ孔など）は同じ形を使う。

- 加工の行には、形に応じた項目をまとめて保存する
- 伝票に載せる文（加工内容）は、保存した項目から組み立てる。組み立てた文は保存しない（項目と文が食い違わないようにするため）
- 形を決めていない加工種別は「自由入力」の形とし、これまでどおり加工内容を文字で入力する。形は加工種別ごとに順に追加していく

**1S/ と数量**

伝票の「1S/」は「1 枚あたり」を意味する。孔数・面数・開口数などは 1 枚あたりの数で入力し、加工の数量は母材（加工がぶら下がる材料の行）の枚数から自動で求める。

| 入力の形 | 加工の数量 |
| --- | --- |
| 穴 | 1 枚あたりの孔数 × 母材の枚数 |
| 曲げ | 母材の枚数（曲げは単価が重量で決まるため、材料と同じ枚数とする。詳細は単価の自動計算の設計時に詰める） |
| 自由入力 | 手入力 |

自動で求める数量は、母材の枚数を変えると追随する。

**加工ごとの入力項目と単価の考え方**

下表は業務側で整理した単価ルールの記録であり、将来の単価の自動計算の設計に使う。MVP で項目入力に対応するのは「穴」「曲げ」の形のみで、それ以外は「自由入力」の形のまま、1 つずつ追加する。加工の仕入単価は、どの形でも MVP では手入力とする。

| 加工 | 入力項目（表記の例） | 単価の考え方 | MVP |
| --- | --- | --- | --- |
| 穴（レーザー・プラズマ孔・ガス孔・キリ孔） | 穴径、1 枚あたりの孔数（`1S/ 12孔 38φ`） | 板厚と穴径の区分で決まる（例: 〜30φ は板厚 × 5 円、〜40φ は板厚 × 6 円）。50φ 以上は個別の単価。キリ孔はキリ径の取り扱いが決まっている | 項目入力 |
| 曲げ | ヶ所数、曲げ方（`2ヶ所 二方曲げ`） | ヶ所数と曲げ方で決まる。隣り合う辺を曲げる二方・三方・四方は追加料金。角度では変わらない | 項目入力 |
| ピアス孔 | 1 枚あたりの孔数（`1S/ 2孔`） | 30φ 未満のレーザー穴として扱い、板厚のみで決まる | 自由入力 |
| 長孔 | 長辺 × 短辺（φ）、1 枚あたりの孔数（`1S/ 2孔 30X12φ`） | 長辺の中に短辺の穴がいくつ入るか（切り上げ）× その穴の単価 | 自由入力 |
| 中抜き | 縦 × 横、形、1 枚あたりの開口数（`1S/ 1開口 100X10`） | 4 辺の長さの合計 × 板厚ごとの係数 | 自由入力 |
| タップ孔 | ねじの呼び、下穴径、1 枚あたりの孔数（`1S/ 4孔 M-12X1.0 下穴〇φ`） | 下穴は 30φ までしかないため、実質板厚のみで決まる | 自由入力 |
| 開先 | 1 枚あたりの面数、1 面の長さ、角度、ルート（`1S/ 2面 35°√0`） | 板厚・長さ（500mm 以下は 1 面単位、超えると 1m あたり）・角度（60° 以上か未満か）で決まる。ルートは単価に関係しない | 自由入力 |
| マーキング | 形（線 / その他）、長さ、ヶ所数 | 100mm 以上は 1m あたり 300 円。100mm 未満は線が 1 ヶ所 30 円、その他が 1 ヶ所 50 円 | 自由入力 |
| 切り込み | 長さ、ヶ所数 | 長さのみで決まる | 自由入力 |
| ショット | 入力項目なし（MVP は通常のショットのみ） | 母材の 1 枚あたりの重量で決まる（5kg 以上は kg 単価、未満は 1 枚単価） | 自由入力 |

どの加工にも最低単価がある。単価の自動計算を実装する際に、加工種別マスタに持たせる。

### 重量の計算

単価も出荷も重量を基準とするため、寸法から重量を算出する。単位はすべて mm で入力する。

| 対象 | 計算式 |
| --- | --- |
| 普通板・角 | 板厚 × 縦 × 横 × 7.85 ÷ 1,000,000 |
| 普通板・円 | 板厚 × 直径² × 6.161 ÷ 1,000,000 |
| 普通板・ドーナツ | 板厚 × (外径² − 内径²) × 6.161 ÷ 1,000,000 |
| 縞板・角 | 単位質量 × 縦 × 横 ÷ 1,000,000 |
| 縞板・円 | 単位質量 × 半径² × 3.14 ÷ 1,000,000 |
| 縞板・ドーナツ | 単位質量 × (外半径² − 内半径²) × 3.14 ÷ 1,000,000 |

ボンデ・ミガキも普通板と同じく比重 7.85 の式で計算する。縞板の単位質量（kg/m²）はメーカーによって異なるため、マスタに板厚ごとの値を保持する。縞板は縞目の見た目がメーカーで異なり、受注時に客先へ確認するため、受注時点でメーカーが確定する。計算処理では種類の名前で分岐せず、単位質量が渡された場合に縞板の式を使う。

ドーナツ形状は外円から内円を差し引くため、外径と内径の両方を受注明細に保持する。ベタ丸・ドーナツの角重量（単価の根拠）は、外径を縦・横とした角の式で求める。

1 枚あたりの重量は丸めずに保証重量の判定・単価計算に使う。合計重量は 1 枚あたりの重量に枚数を掛けた後、小数第 2 位までに四捨五入する（切り捨ては行わない）。1 枚ごとに丸めてから掛けると誤差が枚数倍に膨らむため、配送依頼に用いる重量をなるべく正確にする目的で掛けた後に丸める。

計算処理は画面から切り離した純粋な関数として `lib/pricing/` に実装している（重量は `weight.ts`）。

### 角重量と実重量

請求は角重量（外接する四角形として計算した重量）で行う。材料としては四角で消費しており、端材は歩留まりロスとして自社が負担するためである。

一方、運送会社への配送依頼には実重量が必要になる。角重量で依頼すると実際より重い重量で費用が発生する。そのため両方を保持する。

| 切断区分 | 角重量 | 実重量 |
| --- | --- | --- |
| 寸法切 | 計算 | 角重量と同じ |
| アイトレ | 計算・伝票表示 | 送り状発行の画面で、必要な行だけ手入力（CAD から取得。任意） |
| ベタ丸・ドーナツ | 計算（単価の根拠） | 計算・伝票表示 |

現状はベタ丸・ドーナツの重量を Excel で計算してから伝票に手入力している。伝票に載るのは実重量だが単価の根拠は角重量であるため、重量と金額が一致しない。そこで枚単価で表示することで整合を取っている。システムでは寸法入力から両方を自動算出する。

### 最低保証重量

1 枚あたりの重量が小さい製品でも加工の手間は変わらないため、最低保証重量を設ける。判定には 1 枚あたりの角重量（丸める前の値）を使う。特殊製品は種別の `weight_basis` に従う（ササラは使用材重量、それ以外は角重量）。

保証重量の段は単価の行によって異なるため、行ごとのフラグ（`has_light_tier`）で持つ。

| 1 枚あたりの重量 | 1.5kg の段あり | 1.5kg の段なし | 単価の表示 |
| --- | --- | --- | --- |
| 1.5kg 未満 | kg 単価 × 1.5（5 円単位で切り捨て） | kg 単価 × 2 | 枚単価 |
| 1.5kg 以上 2kg 未満 | kg 単価 × 2 | kg 単価 × 2 | 枚単価 |
| 2kg 以上 | kg 単価のまま | kg 単価のまま | kg 単価 |

1.5kg の段があるのは、普通板・SS400 ベースの切断単価行（材質なし）のシャーリング・レーザーと、特殊製品のベタ丸・ドーナツのみである。SS400 ベースの行は SN400B・SM490A・SN490B・SN490C（材質エキストラで計算する材質）も使うため、それらの材質にも 1.5kg の段が適用される。専用単価を持つ特殊鋼（SN400C・SM400A・TMCP325C・TMCP385C）には適用しない。

保証重量は、エキストラ（材質エキストラ・高炉材加算・板厚エキストラ・大板加算）をすべて加算した後の kg 単価に掛ける。

枚単価の円未満は切り上げる（例: 178.5 × 3 = 535.5 → 536）。ただし 1.5kg 保証の枚単価は 5 円単位で切り捨てる（例: kg 単価 185 → 185 × 1.5 = 277.5 → 275）。5 円単位の切り捨ての結果は整数になるため、追加の丸めは行わない。

特殊製品の例外は、特殊製品種別のフラグで持つ。

- スプライス: 独自の最低保証重量（`min_weight` = 3kg）を持ち、1.5kg / 2kg の段の代わりに「3kg 未満は kg 単価 × 3」とする
- ベタ丸・ドーナツ: 重量にかかわらず常に枚単価で表示する（`always_piece_price`）。2kg 以上は角重量を小数第 1 位に四捨五入して kg 単価を掛ける（社内の計算用 Excel と同じ計算方法）

**小物の別途見積もり**

普通板・SS400 ベースのガス・プラズマで 28mm 以上の行は、1 枚 2kg 未満だと別途見積もりとする（単価表の「2k 以下」欄が「別途」）。これも行ごとのフラグ（`small_piece_quote_required`）で持つ。

マスタに保持するのは kg 単価のみとし、枚単価は kg 単価に保証重量を掛けて算出する。単価表に併記されている枚単価は、この計算結果を読みやすく展開したものであり、例外は設けない。

実装は `lib/pricing/minimum-weight.ts` を参照。

### 明細金額

明細金額の円未満は切り上げる。

| 単価の表示 | 明細金額 |
| --- | --- |
| 枚単価 | 枚単価 × 枚数 |
| kg 単価 | kg 単価 × 合計重量（1 枚あたりの重量 × 枚数 を小数第 2 位までに四捨五入した値） |

kg 単価の金額に丸めた後の合計重量を使うのは、伝票に印字される重量と単価から電卓で検算したときに金額が一致するようにするためである。実装は `lib/pricing/amount.ts` を参照。

加工の行も単位（個 / kg）を持ち、仕入金額を求めて受注の合計に含める。

| 加工の単位 | 仕入金額 |
| --- | --- |
| 個 | 仕入単価 × 数量 |
| kg | 仕入単価 × 母材（加工がぶら下がる材料の行）の合計重量 |

いずれも円未満は切り上げる。受注の合計は、材料の行の仕入金額と加工の行の仕入金額の合計とする。

### 定尺売りの単価

定尺売り（切断を伴わない、定尺サイズのままの販売）は、定尺単価マスタ（`standard_plate_prices`）の kg 単価に合計重量を掛けて金額を求める。

```
金額 = 定尺単価（kg 単価）× 合計重量（定尺 1 枚の重量 × 枚数）
```

定尺 1 枚の重量は、切断品と同じ角の式で求める（縞板は単位質量を使う）。定尺の寸法は次のとおり。

| サイズ | 寸法（mm） |
| --- | --- |
| 3x6 | 914 × 1829 |
| 4x8 | 1219 × 2438 |
| 5x10 | 1524 × 3048 |

定尺売りは切断の手間がないため、最低保証重量は適用しない。材質エキストラ・板厚エキストラなどの加算もなく、定尺単価マスタの値をそのまま使う。該当する定尺単価が登録されていない組み合わせは別途見積もりとする。実装は `lib/pricing/standard-plate.ts` を参照。

### 切断単価の自動計算

単価は積み上げで求める。

```
単価 = 切断単価
     + 大板加算
     + 板厚エキストラ
     + 材質エキストラ（SS400ベースの単価を使う場合のみ）
     + 高炉材加算（受注が高炉材の場合。材質・単価の系統によらず適用）
```

次の場合は単価を出さず「別途見積もり」とする。仕入単価は空欄のまま登録し、単価が決まったら仕入入力の画面で入力する（後述「仕入入力」）。

- 該当する切断単価（特殊製品単価）の行が登録されていない
- 切断単価が NULL（別途）
- 小物の別途見積もりに該当する（`small_piece_quote_required` の行で 1 枚 2kg 未満）
- 材質エキストラの加算が必要なのに、その材質の行が登録されていない（誤った単価を出さないため）

同じ条件の行が料金改定で複数ある場合は、適用開始日（`valid_from`）が受注日以前の行のうち最も新しい行を使う。

実装は `lib/pricing/kg-unit-price.ts`（kg 単価）、`lib/pricing/calculate-price.ts`（別途見積もり・保証重量の判定を含む入口）を参照。

**切断単価**

種類（普通板・縞板・ボンデ・ミガキ）× 板厚グループ × 切断方法（シャー・ガス・レーザー・プラズマ）× 切断区分（寸法切・アイトレ）で決まる。板厚グループの区切りは種類と切断方法によって異なるため、共通の区分は設けず行として保持する。

単価が設定されていない組み合わせは都度見積もりとし、単価を NULL として画面に「別途」と表示する（上記の「別途見積もり」と同じ扱い）。

**大板加算**

板厚ごとに加算値が決まっている（3.2・4.5・6 は +30、9・12 は +15）。板厚グループ単位ではないため、板厚ごとの値をマスタに保持する。

**定尺と大板の判定**

受注明細の商品（`products` の形状 `定尺` / `大板`）と、大板加算をかけるかどうかは、部品の寸法から次のルールで決める。

| 部品の寸法 | 使う商品 | 大板加算 |
| --- | --- | --- |
| 定尺（1524 × 3048）に収まる | 定尺の商品。定尺の商品がない板厚（厚板など大板しか扱わない板厚）は大板の商品 | かけない |
| 定尺を超える | 大板の商品（なければ取り扱いなし） | かける |

- 縦横を入れ替えて定尺に収まる場合も「収まる」とする（例: 3000 × 1000 は定尺に収まる）
- ベタ丸・ドーナツは外径を縦横とした四角形で判定する
- 大板加算は「部品が定尺を超えるため大板から切り出す」ことへの加算であり、大板の商品しかない板厚の小さな部品にはかけない
- 定尺売りは定尺の商品だけを使う

実装は `lib/order-entry/resolve-item.ts`（`fitsInStandardPlate` / `selectProduct`）を参照。

**板厚エキストラ**

25mm を超える板厚に加算する。扱う板厚が 28・32・36・40・45・50・55・60 と不規則な段階であるため、計算式ではなく板厚ごとの加算値をマスタに保持する（28:+1、32:+2、36:+3、40:+4、45:+5、50:+6、55:+7、60:+8）。単価表では 25mm を超える板厚の単価がこの加算込みの値で書かれているため、切断単価マスタには加算分を差し引いた値を登録する。

**材質エキストラ**

材質ごとに、2種類の加算値をマスタに保持する。

| 項目 | 内容 |
| --- | --- |
| 材質エキストラ | SS400ベースの単価にこの材質を使う場合の加算（材質そのものの価格差） |
| 高炉材加算 | 受注が高炉材のときに加算する値。通常 +10 だが SS400 には適用しないなどの例外があるため、材質ごとの値として保持する |

材質エキストラは「SS400ベースの単価を使う場合」にのみ加算する。専用単価（後述）を使う場合は、その単価に材質差がすでに織り込まれているため加算しない。一方、高炉材加算はどちらの単価を使う場合でも受注が高炉材なら加算する。そのため専用単価を持つ材質についても材質エキストラ・高炉材加算の行をマスタに用意する（材質エキストラは使われないため 0、高炉材加算は 10）。

製鋼法（電炉材・高炉材）は客先指定があった場合に単価が変わるため受注時点で確定しており、受注明細に保持する。後から変更できるようにする。受注入力では、材質を選ぶと製鋼法にその材質の初期値（材質マスタの `default_steel_making`。SS400 は電炉材、それ以外の規格材は高炉材）が入り、必要に応じて変更する。ただし定尺売り（定尺単価に高炉材加算がない）と、材質エキストラを適用しない種類（縞板・ボンデ・ミガキ）では製鋼法を指定しない（NULL）。

**材質の 2 系統**

材質は単価の決まり方で 2 つに分かれる。

| 系統 | 材質 | 単価の求め方 |
| --- | --- | --- |
| ベース + エキストラ | SS400、SN400B、SM490A、SN490B、SN490C | SS400 の単価に材質エキストラを加算 |
| 専用単価 | SN400C、SM400A、TMCP325C、TMCP385C | 材質固有の単価表を参照 |

切断単価マスタでは、材質を NULL とした行を SS400 ベースの共通単価として扱い、材質を指定した行はその材質専用の単価として扱う。引く際はまず材質指定の行を探し、なければ NULL の行を使って材質エキストラを加算する。高炉材加算は、いずれの行を使った場合でも受注が高炉材であれば別途加算する。

専用単価の単価表は高炉材の価格で書かれているため、マスタには高炉材加算の 10 を差し引いた電炉材ベースの値を登録する。SN400C・SM400A は切断方法によらず同一単価のため、各切断方法に同額で登録する。

### 特殊製品の単価

スプライスプレート・ササラ・ベタ丸・ドーナツは、切断区分（寸法切 / アイトレ）や重量区分に依存しない製品形態ごとの単価を持つ（切断方法は、単価を使えるかどうかの条件としてだけ持つ。後述「切断方法の条件」）。日常的に発生するため MVP の対象とする。

| 製品 | 単価の決まり方 | 重量の基準 | 備考 |
| --- | --- | --- | --- |
| スプライス | ショット加工の有無（受注単位） | 角重量（3kg 保証） | 切断・キリ孔・ショット込みのセット価格。アイトレは別途見積もり |
| ササラ | 板厚区分 | 使用材の重量（使用材の寸法から自動計算） | 端材を出さない板取りによる特別単価 |
| ベタ丸 | 板厚区分 | 角重量 | 常に枚単価で表示。レーザー以外（ガス・プラズマ）は別途見積もり |
| ドーナツ | 板厚区分 | 角重量 | 常に枚単価で表示。レーザー以外（ガス・プラズマ）は別途見積もり |

**切断方法の条件**

特殊製品は、ガス・プラズマ・レーザーのいずれでも切る（厚い板ではガス・プラズマでベタ丸・ドーナツを切ることもある。シャーリングでは作らない）。ただし特殊製品単価が使えるのは、決まった切断方法の場合だけである。

| 製品 | 特殊製品単価を使う切断方法 | それ以外 |
| --- | --- | --- |
| ササラ | 切断方法によらない（ガス・プラズマ・レーザー） | — |
| ベタ丸・ドーナツ | レーザー | 別途見積もり |
| スプライス | 切断方法によらない | — |

これを種別名の分岐ではなくデータで持つため、特殊製品単価（`special_product_prices`）に切断方法の条件（`cutting_method`）を持たせる。空欄は「切断方法を問わない」とし、値が入っている行はその切断方法の明細だけに使う。ササラ・スプライスの行は空欄、ベタ丸・ドーナツの行は「レーザー」で登録する。ガス・プラズマのベタ丸・ドーナツには当てはまる行がないため、「単価の行が登録されていない組み合わせは別途見積もり」という既存の決まりで自動的に別途見積もりになる。

材質エキストラ（種類が材質エキストラを適用する場合）と高炉材加算はいずれにも適用する。板厚エキストラはベタ丸・ドーナツに適用し、スプライス・ササラでは該当する板厚の受注が希少なため別途見積もりとする（28mm 以上の単価を登録しない）。大板加算はベタ丸・ドーナツのみ適用する。最低保証重量の扱いは「最低保証重量」を参照。

スプライスは請求の基本に合わせて角重量で単価を求める。スプライスは寸法切であり、寸法切では角重量と実重量が同じ値になる。寸法切を前提としたセット価格のため、切断区分がアイトレの場合は別途見積もりとする。これは種別名で分岐せず、特殊製品種別のフラグ（`irregular_cut_quote_required`）で持つ。

スプライスは通常の明細と混ざることがないため、スプライス専用の受注（部材区分が SPL の受注。`orders.member_class = 'SPL'`）として受注単位で扱う。スプライス専用の受注では明細がすべてスプライスとなり、ショットの有無も受注単位（`orders.splice_shot`）で持つ。明細の仕入単価は、このショットの有無で特殊製品単価を引き当てる。スプライスに使う特殊製品種別は、種別名ではなくフラグ（`special_product_types.is_splice_order_type`）で特定する。通常の受注の区分の一覧にはスプライスを出さない。

ササラは階段用の大型部材であり、通常単価では高額になる。切断済みの板の残り部分を使って端材を出さないように配置することで価格を抑える売り方のため、製品重量ではなく使用材の重量に単価を掛ける。使用材の寸法は受注入力時に人が判断して入力し、使用材の重量はその寸法から自動計算する。

### 二次加工の単価

曲げ・開先・ショット・キリ穴・タップ穴、およびレーザー・プラズマによる穴あけ・長孔・中抜き・切り込み・マーキングは、加工種別ごとに単価の決定要素が異なる（穴径と板厚、曲げのヶ所数と曲げ方、母材の重量など）。現状は単価体系に一貫性がなく個別に判断している。

これらを自動計算するには業務側で単価ルールを整理する必要があり、開発とは別の作業になる。MVP では加工明細に単価と単位（個 / kg）を手入力する方式とし、自動計算は Phase2 以降とする。整理済みの単価ルールは「加工の入力項目」に記録している。自動計算に必要な項目が後から取り出せるよう、加工の内容は MVP の時点から項目で入力する。

### メーカーの扱い

メーカーには「指定」と「実績」の 2 つの性質があり、確定するタイミングが異なるため別カラムで保持する。

| 項目 | 確定時点 | 性質 |
| --- | --- | --- |
| メーカー指定 | 受注時 | 客先からの要求。指定がない場合も多い |
| 使用メーカー | 加工時 | 実際に使用した板の実績。ミルシート No. から判明 |

同一カラムで兼ねると、指定のない受注に実績が入った際に客先指定があったように見えてしまう。

商社はミルシートが届くまで判明しないため、商品マスタではなく取引側（受注明細）に保持する。MVP では扱わず、Phase2 のミルシート作成時に設計する。

### 注意事項の表示

注意事項は、性質の違う 2 種類に分けて受注入力時に表示する。どちらも表示のみで、受注には保存しない。登録も止めない。

| 種類 | 何に結びつくか | 表示する場所 | 例 |
| --- | --- | --- | --- |
| 得意先の注意事項 | 得意先（必須）と、切断方法・加工種別（任意） | 受注登録の ② 注文内容の明細の上 | 精度に厳しい / 記号記入はケガキ NG / レーザーのときはケガキマーキング不可でインクジェットマーキング指定 |
| 加工の注意事項 | 加工種別（必須）と、板厚の範囲・穴径の範囲（任意） | 当てはまった加工の行のすぐ下 | キリ孔で穴径 30φ 以上 →「精度注意」/ 曲げで板厚 13mm 以上 →「12mm を超える曲げは要確認」 |

**得意先の注意事項**

得意先・切断方法・加工種別のうち、指定した条件がすべて受注に当てはまったら表示する、という 1 つのルールで判定する。切断方法と加工種別は、受注のどこかの行にあれば当てはまるとする。得意先だけを指定したものは、その得意先の受注すべてで表示する。

各注意事項には、指定した条件を並べた印（「得意先」「得意先 × レーザー」「得意先 × キリ孔」など）を付け、なぜ表示されたかが分かるようにする。

現状は「スプライス表」などの Excel を都度開いて五十音順のシートから該当先を探している。得意先を選択した時点で自動表示される形とし、探す作業そのものをなくす。

**加工の注意事項**

加工の可否や注意は、得意先ではなく加工と材料の条件で決まるものが多い（板厚が厚いと曲げられない、穴径が大きいと精度が出にくい など）。そこで得意先の注意事項とは分け、加工の行ごとに判定する。板厚は加工の行の母材（材料の行）から、穴径は加工の行の入力（入力の形が「穴」のとき）から取る。範囲はどちらも「以上・以下」で、片方だけの指定もできる。

受注全体の注意事項の枠ではなく、当てはまった加工の行のすぐ下に表示するのは、どの行の注意かがすぐに分かるようにするためである。

**共通の考え方**

受注に関係のない注意事項は表示しない。関係のないものまで出すと、件数が増えるにつれ読み飛ばされ、注意喚起として機能しなくなるためである。範囲で表せない条件付きの内容（この曲げ方は要相談、など）は自動判定せず、テキストとして表示する。

### 帳票印刷

ブラウザ印刷（CSS の `@media print`）で実装する。単価の表示・非表示を印刷前に切り替えられるようにし、現行の「現場用」「単価記入用」の使い分けに対応する。

MVP で出力するのは現場用伝票・加工図面・製品ラベル・送り状の 4 種類。現場用伝票は受注登録と同時に、加工図面と製品ラベルは加工図面発行（現場加工指示）のメニューから出力する。加工図面は受付に保存された注文書に受注情報を添えて印刷する。

事務所（事務・CAD）はペーパーレスとし、受付〜受注登録待ちの範囲では印刷しない。現場は今まで通り紙で運用するため、現場に渡る一式（現場用伝票・加工図面・製品ラベル）は印刷する。

製品ラベルの枚数（梱包数）は、受注後のラベル発行メニューで明細ごとに手入力する。梱包の分け方には例外や現場判断が入るため、システム側では自動計算しない。受注時点では決まっていないことが多いため、受注登録画面では入力しない。

加工図面は受付に保存された注文書 PDF（追加分を含む）を印刷する。

### 現場用伝票の表現

現場用伝票は現場が読み取りやすいことを最優先とする。現状はマーカーや手書きで毎回書き加えているが、判断基準が明確なものは印刷時に自動反映する。

**材質による自動表現**

材質ラインは材質ごとに色と本数が決まっているため、材質マスタに登録し、現場用伝票に具体的な指示として印字する。「材質ライン要」とだけ記すのではなく「材質ライン：青2本」のように出すことで、現場が別途確認する手間をなくす。伝票上の表示色も材質マスタから取得する。

基本の材質（SS400）はラインの登録がないため何も印字されない。印刷処理では材質名を条件分岐せず、ラインが登録されていれば印字するという判定のみを行う。

板厚ごとの区切り線も、明細を板厚でグループ化することで自動的に引ける。

**スタンプ文言**

「雨濡れ厳禁」のように、受注ごとに付けたい文言はスタンプ方式で扱う。文言をマスタとして登録しておき、受注入力時にチェックを入れたものが伝票に印字される。スタンプには番号を付け、受注入力ではテンキーで番号を打って付け外しする。

得意先による客先指定の文言は、得意先に紐づけて登録しておき、受注入力時に初期状態でチェックが入った状態とする。その受注だけに必要な場合は手動でチェックする。

毎回手書きする手間がなくなるほか、文言の表記ゆれも防げる。

スプライス専用の受注でショットが有の場合は、「ショット加工」を自動で付け、現場用伝票の目立つ位置に印字する。入力者が外すことはできない。ショット加工の有無は受注（`orders.splice_shot`）から印字し、スタンプとしては保存しない。ショットの有無と伝票の表示が食い違わないようにするためである。

**フリーコメント**

現場用伝票はイレギュラーな指示が発生しやすいため、自由に記入できる欄を設ける。受注全体に対するフリーコメント（改行を入れられる）を、受注登録の ② 注文内容の明細の下の帯で入力する。特定の明細だけに適用する指示（「3 行目は端材を返却」など）も、フリーコメントに書く。明細ごとの摘要の欄は、行ごとに Enter で進む手間がかかり、ほとんどの行が空欄になるため使わない（DB の列は残す。table-design.md `order_items`）。

### 送り状発行

受注番号に紐づけて出荷日・出荷数量を入力する。受注数量・残数量・出荷数量を管理し、分割出荷に対応する。

発行操作によりステータスを「配送依頼済み」に更新する。配送部システムへの実際の通知・連携は Phase2 とする。

送り状を発行した受注は、修正・削除できない（後述「仕入入力」の「修正の順番」）。

### 仕入入力（予定）

仕入単価を確認・入力し、仕入を計上する画面。今回は実装せず、予定として記録する。業務の流れ「受注 → 送り状 → 仕入」の最後の工程で、送り状を発行した後に行う。

**できること**

- 別途見積もりで空欄のまま登録した仕入単価を入力する
- 受注登録で自動で入った単価を確認し、一括で仕入を計上する
- イレギュラーな単価（値引き・特別な取り決めなど）を修正する
- 加工の行の単位（個 / kg）と仕入単価を入力する

**仕入の計上**

仕入を上げると、仕入No. を採番し、仕入日と締日を記録する。

**修正の順番**

修正は逆順でしか行えない。

1. 仕入を削除する
2. 送り状を削除する
3. 受注を修正する

- 仕入がある送り状は削除できない
- 送り状がある受注は修正・削除できない。今ある「出荷実績がある受注は削除できない」制限（DB のトリガー）を、修正にも広げる形にする

**未決事項**

- 分納（分割出荷）のとき、仕入を送り状ごとに上げるか、受注ごとに上げるか

### ファイル管理

注文書・図面を受付に紐づけて保存し、受注からは受付・加工区分を通してたどる。現状は客先ごとのフォルダにファイル名を付けて保管しているが、受注番号から関連ファイルへ到達できる形に変える。事務側の手配ミスが疑われた際に、受注内容と注文書を突き合わせて確認できるようにするためである。

ファイルは受付の時点で保存する。メール・FAX の添付はそのまま受付に入り、振り分けた DXF・CAD の CSV・見落として後から追加した図面も、同じ受付に保存する（`intake_files`。docs/intake/table-design.md）。注文書をスキャンしてアップロードする工程はなくなる。手書きの注文書や口頭の注文のメモは、受付の「手動で受付を追加」で PDF にして登録する。

受注に直接ファイルを付ける `attachments` は使わない。ファイルの置き場所を 1 つにして、受付と受注で別々に同じファイルを持たないためである。

### 加工図面の印刷

受注番号を指定すると、その受注の受付に保存された注文書が表示される。これを印刷する際、受注データから以下の項目を別枠に印字する。

売り先 / 納入先 / 工事名 / 納期 / 受注番号

これらを印字するのは、現場用伝票と加工図面が別々の経路で動くためである。伝票は製品とともに工程間を移動する（切断 → 穴あけ → 曲げ）が、図面は事務所から加工先へ直接渡る。現場で両者が同一の受注のものだと判断できる必要がある。

図面への直接の書き込みは MVP では行わない。曲げ加工時の板の伸び値など、図面上の位置と結びついた指示は従来どおり手書きで対応する。図面上に注釈を配置する機能は Phase2 とする。

## 権限設計

### ロール

| ロール | できること |
| --- | --- |
| 事務 | 受注登録・編集、送り状発行、帳票印刷、進捗確認 |
| 現場 | 加工指示の閲覧、ステータス更新（加工完了） |
| 管理者 | 上記すべて、およびマスタ管理 |

価格マスタは管理者のみがアクセスできるものとする。仕入単価は経営に直結する情報であり、現場が売上単価・仕入単価を参照する必要もない。現行の加工指示書が「現場用」と「単価記入用」に分かれているのも、単価を見せる相手を限定していたためである。

ただし受注登録では、事務が仕入単価を自動計算する必要がある。そのため、明細の条件に該当する価格マスタの行だけをデータベースの関数（`security definer`）で取り出し、計算は `lib/pricing` で行う。事務ロールは計算に必要な行だけを取得でき、価格マスタの一覧（単価表そのもの）は引き続き管理者のみが参照できる（table-design.md「価格マスタの権限と単価計算」を参照）。

### 現場ロールの扱い

現場には現時点で PC がないため、現場アカウントは運用しない。ただしロールの枠組みと RLS による制御は MVP の段階で用意する。権限設計はテーブル構造や画面の作りに影響するため、後から追加すると広範囲の手直しが必要になる。一方で、定義したロールを運用しないことによるコストは発生しない。

現場向けのタブレット用画面は作成しない。実機の導入が決まってから、実際の使われ方を確認しながら設計すべきものであり、PC のない状態で想像に基づいて作っても使われる形になる保証がない。

### 受付〜受注登録待ちのテーブル

受付・振り分け・CAD・受注登録待ちのテーブルは、事務・管理者が読み書きでき、現場は参照できない（docs/intake/table-design.md「RLS・権限」）。受付の作業は事務所（事務・CAD）の業務であり、現場の業務範囲に含まれないためである。ホームの目安納期は全社に見せるため、すべてのロールが参照できる。

### 部署と営業所

ユーザーには、ロールとは別に部署（営業部・加工部・シャーリング部・配送部・経理/総務）と所属する営業所（本社・A営業所・B営業所）を持たせる。部署は通知の宛先（受付の新着はシャーリング部の全員）に、営業所は受付登録の加工場所の初期値とヘッダーの表示に使う。権限はロールで決め、部署・営業所では決めない。

### ログイン

画面では社員No. とパスワードでログインする。Supabase Auth はメールアドレスでログインする仕組みのため、社員No. から決まった形のメールアドレス（`{社員No. を小文字にしたもの}@staff.invalid`）を作って渡す。`.invalid` は実在しないことが保証されたドメインで、メールは送らない。社員No. からメールアドレスを調べる関数を作る方法もあるが、どの社員No. が存在するかを外から確かめられてしまうため採らない。

ユーザーは管理者が Supabase の管理画面で、この形のメールアドレスで作成する。`users.employee_no` は一意とし、作成時にメールアドレスから自動で入れる。

### 実装方針

認証は Supabase Auth を使用する。権限制御はクライアント側の表示制御だけでなく、Supabase の RLS（Row Level Security）によってデータベース側でも強制する。

前作の在庫管理システムでは、管理者専用画面の制御がクライアント側のみでサーバー側が未実装という課題が残っていた。本システムではこれを解消し、現場ロールのアカウントが単価情報を参照できないことを DB レベルで保証する。

前作の在庫管理システムと同一構成とし、技術選定に時間をかけず設計と実装に集中する。ファイルの保存に Supabase Storage、受付の新着の通知と一覧の自動更新に Supabase Realtime を新たに使用する。

### 主要な設計判断

**ステータスをカラムとして保持する**

前作では在庫ステータス（在庫あり・要補充・在庫切れ）を動的計算で求めた。現在庫と基準数から必ず一意に決まるためである。一方、受注のステータスは「現場用伝票が戻る」など人の操作や出来事によって変わるものであり、計算では導出できない。そのためカラムとして保持する。

**ステータスを受注ヘッダー単位とする**

実務では同一受注内の明細がまとめて加工・出荷されるため、明細単位のステータス管理は行わない。作れる構造を作るのではなく、業務の実態に合わせて設計を簡素化した。

**残数量を保持せず計算で求める**

出荷の取り消しや修正の際に整合性が崩れることを避けるため、残数量はカラムを持たず「受注数量 − 出荷実績の合計」として算出する。前作の在庫ステータスと同じ考え方である。

**価格ルールをデータとして持つ**

条件分岐をコードに記述せず、マスタの行として保持する。単価は「切断単価 + 大板加算 + 板厚エキストラ + 材質エキストラ + 高炉材加算」の積み上げで求まるが、高炉材加算を SS400 には適用しないといった例外があるため、材質ごとの値をデータとして持つ。料金改定時にマスタの更新のみで対応でき、実装に手を入れる必要がない。

**重量区分を入力させない**

重量区分（最低保証重量の適用有無）は寸法と材質から算出できるため、入力者に選択させず自動判定する。業務上必要な項目のみを入力対象とする。

**将来の拡張を見据えた粒度の設定**

商品マスタを「種類 × 材質 × 板厚 × 形状」とし、メーカーを含めない。受注時点では使用する板のメーカーが確定しないためである（縞板のみ、縞目の見た目が異なるため受注時に確定する）。この粒度は既存の在庫管理 Excel（材質 × 板厚でシート分割、内部でメーカー別に管理）とも整合し、Phase2 での在庫連携時に「SS400 22mm が在庫薄」といった表示を無理なく実現できる。
